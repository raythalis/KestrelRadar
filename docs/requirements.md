# Kestrel 需求文档 v1.0

## 0. 项目与参考

- 项目名 **Kestrel**（红隼）；前身是 radar-v2（已停用删除，名字只作历史）。
- 开源项目，public 仓库，通用性优先：不绑定我自己的环境，任何人的 RSSHub / Ollama / 远程模型都能配。
- 参考：**folo**（页面样式与「发现」的交互形态）、**MoviePilot**（通知渠道的配置形态）。
- 通知渠道实现方式已核实：MoviePilot 是**自研**（每个渠道一个模块、自带连通性测试，依赖里没有任何通知聚合库，全仓只在测试基线文件里出现过一次 apprise）。所以没有现成轮子可省，Kestrel 同样自研。
- 技术栈与工程约定（已定）：单仓 monorepo（pnpm workspaces，固定 pnpm 12.8.1）；前端 Vue 3 + Vuetify + TypeScript；后端 Node + TypeScript（Fastify + Zod + SQLite）；Prettier 单引号、无分号、100 列；开发分支 develop、成品分支 master；个人/本机专用配置放 local/（已被 gitignore，不进远端）；仓库不包含成人相关内容与任何私人基础设施信息。
- 开发形态：开发期在本地直接跑 Vite（默认 5173 端口）做热更新，开发机不装 docker；到打包阶段再根据平台支持 docker、PWA 或 electron。
- 需要考虑到为移动端支持样式：**桌面端三列并排，移动端在同一分组内用「发现 / 监听 / 动作」标签切换**（已确认）。

## 1. 全局外壳

- 右上角：i18n 切换（目前中文 / 英文）、主题切换（白天 / 黑夜 / 跟随系统）。

## 2. 仪表盘（v1.0 先占位）

- 计划展示：RSSHub 状态、源数量、采集数量等。
- v1.0 先搭占位骨架、标注「未接入」，具体指标等后续功能起来再定。
- 采集到的结果列表（条目/事件）先放在仪表盘里，**包括被判定为「没命中」的内容**（默认筛选隐藏，可切换查看）。

## 3. 配置管理（核心）

### 3.1 整体结构

- **分组**：折叠块形态，字段为分组名称 + 分组简介；支持收起、展开、新增、编辑、删除。分组可以批量删除。删除操作要有确认弹窗。
- 分组头部包含：折叠箭头、名称、简介、三列计数（几发现 / 几监听 / 几动作）、整个分组的启用开关、编辑与删除入口。
- 折叠态只显示一行摘要（名称、简介、计数）；**同一时刻可以展开多个分组**，有全局折叠或展开按钮。
- 展开后是**三列**：发现 / 监听 / 动作。左→右是一条流水线：来源 → 判定 → 通知。
- 每列都能添加多个条目；列头显示计数和「+」；列头下一行小字说明该列作用。
- **监听之间是「或」关系**。
- **分组停用的语义**：停用 = 不再采集、不判定、不投递（库里已有数据全部保留）；重新启用后按原频率继续。
- **发现停用 / 删除的语义**：停用 = 不再抓取它（已有的条目与事件保留）；删除 = 只删这条发现本身，**它的历史条目与事件一律保留**（删除确认弹窗里要写明这一点）。
- 界面设计稿：`apps/web/public/design/config-management.html`（静态预览稿）。

### 3.2 发现（左列）——内容从哪来

- 支持四类发现：RSSHub 路由、网页地址（URL）、RSS 源、关键词。
- v1.0 只做前三类；**关键词自动发现延后**（folo 那种「输入关键词自动找到可订阅源」的机制还没核实，先不做）。
- RSSHub 路由 v1.0 采用**方案 A**：用户直接粘贴路由地址，带参数的路由由用户自己填完整地址。
  第二步再做方案 B（连上 RSSHub 拉出全部路由目录、按网站分组展示、点选后弹表单填参数、自动拼地址）。A 与 B 共用同一套试抓校验逻辑。
- 卡片内容：类型标签、路由/地址、启用开关、测试状态、最近测试时间、**该源最近一条的时间与大致更新频率**、**下次采集时间**（由调度器算，不入库）。
- **每个发现单独配采集频率**：用 cron 表达式，界面上给一个**方便配置的定时组件**（预设 + 高级模式）。没有全局默认频率。
- **定时表达的是「多久去看一眼」，不是「取哪个时间段的内容」**：每次抓取就是把源当前的内容拿回来，然后跟「上次见过的」比，没见过的就算新内容。所以「每小时抓一次」= 每小时去看一眼、把上次之后新出现的收进来；「每天 4 点抓一次」= 每天 4 点去看一眼、把从昨天 4 点之后新出现的收进来。用「上次见过」而不是时间窗来取内容，对延迟发布、不按时间排序、时间字段有错的源都成立，不会漏。
- 时间窗口和抓取频率是两件事：频率管「看得勤不勤」，窗口管「多旧的就不要」（见下面的新鲜窗口）。界面上也分开显示，避免混淆。
- **测试（只有「发现」有，分两级）**：
  - ① 路由连通性：RSSHub 实例可达 + 该路由返回合法内容流。能区分出「实例不可达」「这条路由需要参数」「这条路由需要凭证或需要浏览器渲染」。
  - ② 内容连通性：解析返回结果，看条目数、最新一条的时间。
  - 结果就地显示两个灯（路由 / 内容），失败时给一句人话说明是哪种原因。
- **不做全局「定期自动测试」**（2026-10-01 调整：发现本身就是定时的，每次定时采集就等于在做一次连通性测试，再定期测一遍是重复劳动）；只保留每张卡片上的手动「测试」按钮。
- 新增发现时先自动测一次，通过才允许保存，避免存进一堆死源。
- **首次采集建立基线后**，卡片上显示一行说明：「已建立基线：收入 N 条历史内容，不计入推送」，让用户知道为什么刚加源没收到通知。
- RSSHub 实例地址本身也是路由层测试对象：实例不通，则该分组下所有发现一起变红。
- **怎么判断两次抓取之间多了什么**：不保存整页内容去比对，而是**逐条算指纹**。
  - 每条内容生成一个稳定指纹（优先用规范化后的链接：去掉追踪参数、统一大小写与末尾斜杠；没有链接时用标题 + 正文片段的规范化结果），库里按「来源 + 指纹」唯一。
  - 每次抓取逐条查：查不到 = 新内容（进入判定）；查到 = 老内容（只刷新「最近见到的时间」）。
  - 为什么不比对整页：页面上无关的变动（阅读数、点赞数、排序变化、广告）会让整页时时刻刻都「不一样」；源通常只返回滚动窗口，老内容掉出页面还会被误判成「消失了又出现」；而且整页体积大、比较慢。
  - 不变式：一条内容的「发布时间」和「首次见到的时间」写入后不再改，「最近见到的时间」每次抓到都刷新；同一条内容抓一百次也只有一个条目。
  - 去重的范围是**同一个来源内**（「来源」= 一条发现）；跨来源出现的相同内容不做条目级去重，交给事件归并去合并——这俩是两回事：指纹去重管「同一条内容」，事件归并管「同一件事」。
  - 同一条路由被两个分组各加一次时，两边各存一份、各算各的（符合「分组之间独立」），互不影响。
- **时间处理（重要）**：不能假设源里的内容都是最新的、也不假设它按时间排好序。
  - 三个时间分开存：来源给的**发布时间**（没有就是空）、**首次见到的时间**（重复采集不变）、**最近见到的时间**（每次刷新）。
  - **新鲜度不是过滤条件，只是排序权重**：绝不因为「这条有点旧」就把它筛掉——否则抓取间隔长的源（比如 24 小时抓一次、内容可能 23 小时前发布）会被误杀。它只用来在同一批内容里决定谁排前面。
  - **真正挡住旧内容的是另外两条规则**：① 每个源**第一次采集只建立基线**——这一刻之前页面上已经存在的内容全部存下来，但不参与投递；之后每次新出现的才算新内容。② 一个可配的**新鲜窗口**（暂按 7 天，天数待压测定）兜底，只对「来源明确写了发布时间、且明显过旧」的条目跳过投递（榜单类源会把老文章翻上来，靠这条挡住）。窗口默认偏宽，避免周更之类的慢速源被误伤。
  - 拿不到发布时间就用「首次见到的时间」，并在界面上标注这是退化的。**绝不把抓取时间当成发布时间**，否则榜单类源每次刷新都会被当成刚刚发生。
  - 窗口怎么判断，举个例子：今天是 10-01，某条内容写着「发布于 09-20」。它我们没见过，所以算新内容，但发布时间离今天已经 11 天、超出 7 天窗口，于是**只存不推**（仪表盘能查到）；写着「2 小时前」的就正常参与投递。**没写发布时间的内容一律按「首次见到」算，永远不会超窗**，所以这条规则只对「明确写了旧时间」的内容生效。
  - **源不一定有时间**（实测一个本地 RSSHub 实例：GitHub 趋势路由 17 条内容**全部没有发布时间**；36氪快讯 20/20、Hacker News 30/30 都有）。所以「没有时间」是常态而非异常：没有时间就走降级，不影响命中判定，只是新鲜度排序退化为中性。
  - 时区：能带时区的时间按它自己带的时区解析；只给本地时间且没带时区的，按源所在时区（默认应用时区）解读，转成统一时间存储、显示时按用户本地时区渲染。识别不出时间的就置空走降级，不猜。
  - 时区不在定时组件里暴露（避免增加配置负担）；应用时区跟随系统，高级设置里可改。

### 3.3 监听（中列，核心逻辑）——什么算命中

**判定是一个四层漏斗，每一层都能被用户看懂，默认偏松（宁可多推一点，也别把想看的漏掉）：**

1. **来源范围**：这个分组里启用的发现，决定「能看到什么」。
2. **关键词门槛**：填了就作门槛（任意命中 / 全部命中），不填就是**全部通过**（默认宽）。排除词单独一层，可以勾选「追加全局排除词」。
3. **打分**：对通过门槛的内容算一个相关度分数，分三档——**高分直接放行、低分直接丢掉、中间灰区**才算拿不准的。
   - 打分信号：关键词命中的强度（命中几个、命中在标题还是正文）、来源权重、内容本身的一些信号。全部可解释。**时间新鲜度不参与命中判定**（它只用于排序），避免抓取间隔长的源被误杀。
   - **灰区的处理分两种模式**：算法模式（纯算法）下灰区**默认放行**（保守偏向不漏）；算法 + LLM 模式下，灰区交给 LLM 复核，回「是 / 否 + 一句理由」，判否的就丢掉但会记录理由。
   - **为什么 LLM 只做灰区、不做加分项**：加分会让分数变成玄学（用户分不清结论是权重给的还是模型给的），而且逐条调用很贵。让 LLM 只裁决灰区，既省钱又能一句话解释清楚。
   - 监听卡片上只暴露一个**灵敏度**（宽松 / 标准 / 严格），映射到全局那两条线；具体数字在高级设置里解锁才能改。
   - 两条线的默认数值先给一套，等真实数据跑起来再定，不提前调参凑结果。
4. **语义化意图（可选，只在「算法 + LLM」模式下生效）**：用户可以写一句人话，比如「杨幂的新电影」。
   - 关键词层做不了语义：那七个字连在一起几乎什么都匹配不到。所以这类需求交给 LLM 去读懂，字段就叫「意图描述」。
   - **推荐用法**：关键词给一两个粗词（例如「杨幂」）先把范围缩小，意图描述让 LLM 判断「是不是新电影」。关键词负责便宜地缩小范围，LLM 负责读懂语义——两层配合才省钱。
   - **允许不填关键词、只填意图描述**（前提是这条监听开了 LLM）。代价是 LLM 要逐条判全部内容，界面要给出成本提示。

**其他要求：**

- 每条卡片的字段：名称、模式（跟随全局 / 自带算法 / 算法 + LLM）、关键词（多个）、匹配方式（任意 / 全部）、排除词（多个）+ 追加全局排除词、意图描述（可选）、灵敏度、启用开关。
- **判定理由要记录**：命中了哪些关键词、分数多少、落在哪一档、LLM 说了什么。用户能一条条看懂「为什么推 / 为什么不推」。
- **规则预览**：监听卡片上能拿最近采集到的内容试跑一次，显示「这批内容里会命中几条」并列出两三条例子和理由，让用户直观判断规则是松还是紧。
- **安全阀**：所有没命中的内容**照样存下来**，在仪表盘列表里能查到（默认隐藏），并且能一键把内容里的某个词加进关键词（若该分组有多条监听，点的时候让用户选加到哪条）。没有这条回退路径，漏判就永远看不见。
- **动作绑定**（v1.0 方案 B）：
  - 动作是**分组级**的，默认对本分组所有监听生效。
  - 监听卡片上可**选择性覆盖**：只有需要区分时才指定「这条只走某几个动作」。
  - 动作卡片上显示一行只读信息：「当前被哪些监听引用」。
  - 被限定过的监听卡片打醒目标记（例如「仅走 X」）。
  - 理由：默认必须是「会通知」而不是「要配置才通知」——静默失保（采到了、命中了、但你永远收不到、也没有报错）是这类系统最糟的失败模式；同时声明在监听卡片上最符合直觉（正在配这条监听，顺手说命中后走哪几个动作）。

### 3.4 动作（右列）——命中后怎么办

- 每条卡片的字段：名称、触发方式（发现即发 / 每天汇总定时）、通知渠道（下拉选择通知渠道管理里配置的实例别名，末尾「+」跳转到通知渠道页新建）、消息模板、汇总时的定时、启用开关。
- v1.0 **两种触发都要**。汇总定时先给简单模式（每天 HH:MM），需要时再开放自定义定时表达式；时区不暴露，跟随应用时区。
- 异常提示就地显示：未选渠道、未设定时等，在卡片里给黄色提示条。

**归并与投递规则（v1.0 定稿）：**

- **归并的单位是「动作」，不是「监听」**，所以「监听可以指定动作」这件事不会让归并变复杂。
- **先理解三个层次**：**条目**（一次抓取里的一条内容，比如一条微博）→ **事件**（同一件事，可能由多个条目组成）→ **投递**（一个动作的一次发送，里面装着若干个事件）。
- **归并的范围是整个分组**（不是「这一批」）：新条目会跟这个分组里最近一段时间已存在的事件比对，像就并进去、不像就新建一个事件；跨分组不比较。
- **判定在条目层，投递在事件层**：每条内容各自过关键词和分数（更准也更省），归属到事件后，只要事件里有条目命中，这个事件就算命中；动作发送时按事件聚合。
- **事件归并**（内容层面，独立于动作）：同一个事件被多个来源提到时合并成一条事件。
  - 指向同一个链接（去掉追踪参数后相同）→ 一定是同一个事件，直接合并。
  - 链接不同但内容高度相似（例如两个账号发了同一条新闻、各自带自己的分享链接）→ 用文本相似度 + 时间接近 + 同分组判断，**宁可漏并也不硬并**，判不准就分开显示。
  - 归并只影响通知形态，**不删任何原始条目**；被并起来的内容可以展开看到全部来源。
  - **跨分组不归并**，分组之间各算各的。
- **每个事件在通知里显示「有几个来源触发」**（例如「3 个来源提到」），可以展开看全部来源与各自链接。多来源本身就是热度信号。
- **动作内部合并**：一个动作的一次发送里，多条命中合并成一条消息；动作卡片上可以关掉（关掉就是一条一条发）。
- **不同动作之间不合并**：即时推送和每天汇总是两种不同的投递行为，混在一起反而看不懂。
- **同一轮里发往同一个渠道实例的多个动作**：按渠道合并成一条外发（至少做几秒的小窗口合并），避免同一秒刷屏。
- **已投递的事件又收到新条目时（默认不重复推）**：场景是——A 发的微博已经推给你了，过一会 B 发了同样的内容被发现。处理是：新条目归并进同一个事件，来源数从 1 变成 2、最近一次见到的时间刷新，但**不再发一条通知**（否则关注的人越多越吵）。
  - 只有出现**显著新进展**时才允许为同一件事再推一次，通知里标「有更新」。算进展的条件（满足任一）：① 这件事第一次出现**高可信来源**（之前只有小道消息，现在官方账号或官网也发了）；② 内容里出现**明确的进展信号**（发布、上线、开源、停服、涨价、收购、漏洞、修复、定档等，或出现新的版本号）；③ 新增独立来源数达到阈值（只当辅助信号，单独命中不触发）。
  - **不算进展**：同一来源重复转载、换个人转述同一件事、措辞不同的同义标题、单纯条目变多。
  - 事件状态流转：新建 → 已投递 →（有进展时）有更新 → 投递后回到已投递；长期没有新条目的事件自动归档，不再参与比较。
  - 保险：更新投递也受每日投递上限约束，避免一堆事件同时「有更新」把手机刷爆。
  - 连带后果：「几个来源提到」这个数字不会因为新来源出现就立刻发给你，只在下一次推这条事件时才体现（第一次推时显示的是当时的来源数）。
- **幂等**：每条内容在每个动作上**最多被通知一次**（记录「内容 × 动作」的已投递状态）。这条同时解决了「先汇总后立即」「先立即后汇总」的交错问题——已经在这个动作上投递过的不会再发。
- **汇总窗口** = 上次汇总之后**在这个动作上还没投递过的**命中（用投递记录判断，不去算时间窗，避免边界那条被漏掉或发两遍）。
- 汇总动作上有一个开关「**包含已即时推送过的内容**」，默认关（关了就是即时推过的不再进汇总）。

## 4. 通知渠道管理

- v1.0 只做两类：**Telegram**、**Webhook**（通用）。
- 形态参考 MoviePilot：同一类渠道可以配置多个实例、自定义实例别名；有连通性测试按钮；密钥以圆点显示、旁边眼睛图标切换显隐。
- 连通性测试对通知渠道意味着真的发一条测试消息（有副作用，只能手动触发）。
- 渠道与分组的关系：由分组的**动作**选择渠道（不做渠道反向配置分组）。
- **消息模板**：给一套默认模板，并**文档化自定义语法**（用户可以自己改模板）。模板里能用的变量包含：事件标题、摘要、原文链接、**来源数量**、来源列表（各来源名称与链接）、命中时间等。默认模板里就含「几个来源提到」。通知的语言由模板决定（默认模板给中英两套、跟随界面语言；用户自定义后完全按用户写的来）。
- 后续可扩展（不在 v1.0）：企业微信自建应用（企业ID + 应用 AgentId + Secret + 代理）、企业微信群机器人（webhook）、iLink 个人微信（扫码登录、会掉线、有风控）、聚合推送服务（Server酱 / PushPlus / WxPusher，注册给 key + 地址，实现最简单）、公众号模板消息（要认证与审核，不推荐）。
- Apprise（一次支持上百种渠道）只作备选：它是 Python，要单独跑侧车，与全栈 TS 目标冲突，v1.0 不用。

## 5. LLM 管理

### 5.1 模型清单

- 界面是一张**清单**：每行 = 服务商 + 模型（形态参考 Hermes 桌面版的「设置 > 模型 > 备用模型」）。
- 每行可拖动排序、可单独启用 / 停用；**fallback 按清单从上往下依次尝试**。
- **v1.0 只有一处用模型**：灰区复核（语义化意图走的是同一次调用）。所以不需要单独的「判定专用模型」——判定就用清单从上往下第一个可用的。以后出现别的用途（例如给通知生成一句话摘要）再按用途指定模型。
- **v1.0 只有一处用模型**：监听判定里的灰区复核（可选的「意图描述」属于同一件事）。不做摘要、翻译、聚类、embedding，也不用向量检索。既然只有一处，就不设单独的「判定专用模型」配置项——清单里第一个可用的就是判定用的；将来真出现第二处用途再谈分工。

### 5.2 服务商

- 类型：本地（Ollama）或远程（OpenAI 兼容 / Anthropic 等）。
- 配置项：地址、密钥、启用开关、排序。
- 配好服务商后**自动拉取它的模型列表**：OpenAI 兼容用列模型接口，Ollama 用它的 tags 接口；拉回来后勾选要用的、排序。
- 个别中转站不支持列模型接口的，提供「手动填模型名」兜底。
- 连通性测试：拉一次模型列表即验证连通；真发一句话会花 token，所以不默认自动跑。

### 5.3 失败处理

- 全部模型都失败后怎么办，由高级设置里的降级开关决定：**自动降级到纯算法判断** 或 **直接报错**（二选一，用户可切换）。

## 6. 高级设置

- **RSSHub 配置**：实例地址 + **可选的访问密钥**（有些实例带 token）。RSSHub 只有一个实例，密钥跟实例地址放在一起配（全局），**发现上不单独配密钥**。
- **全局判断模式**：自带算法 / 自带算法 + LLM。全局配置，监听里可以选择「跟随全局」或自定义单独的逻辑。
- **LLM 失败自动降级逻辑**：降级到纯算法 或 直接报错。
- **全局排除词**：监听可以选择是否追加全局排除词。
- **打分参数**：默认**不可编辑**；用户开启编辑时需要提醒「如果不懂不要更改」；提供**一键恢复默认**功能。开发阶段全部参数都暴露。
- **采集的调度策略**：超时与失败重试（次数 / 间隔）在这里配，有默认值。
- **数据保留**：条目/事件保留多久、是否自动清理，在这里配（默认 90 天，见第 10 节定案）；事件长期没有新条目（默认 14 天）自动归档，不再参与比较。
- **投递上限**：每天最多推多少条（含「有更新」的补推），在这里配；**默认不限**（2026-10-01 定：静默丢通知比刷屏更糟，要限的时候用户自己填数字）。
- **抓取并发**：同时最多抓几个源，在这里配（默认 5，见第 10 节定案）。全局一个数字，不做按源覆盖。
- **应用时区**：默认跟随系统，可手动改。

## 10. 性能与负载预期

- **指纹查重本身几乎不花资源**：一轮抓下来几十条内容，就是一次批量查询，毫秒级；瓶颈从来不在比较，而在「抓多少源、多久抓一次」。
- 按 **20 个源、每小时一轮、每源每轮 5 条新内容** 估算：每天新增约 2400 条、每天约 480 次 HTTP 请求、每天约 1.4 万次指纹查询；一年累计约 88 万行、约 0.65 GB。
- 配合数据保留（高级设置，默认 90 天）：库里稳定在约 22 万行 / 165 MB；100 个源的规模约 108 万行 / 824 MB。SQLite 在这个量级很轻松。
- 真正需要控制的是三件事：① 抓取并发（默认同时 5 个左右，超时与重试在高级设置里配）；② 失败隔离（单个源挂了不能拖死整轮）；③ LLM 调用量（只有新内容里的灰区才调用，是整个系统唯一持续花钱的部分）。
- 后端进程很轻（Node + SQLite，常驻内存一两百 MB 量级），和其他自托管服务共存没问题。
- 必须建的索引：来源 + 指纹的唯一索引（查重用）、时间字段索引（排序与清理用）。

### 默认值定案（2026-10-01，按人工计算）

| 项 | 默认值 | 说明 |
|---|---|---|
| 抓取并发 | **5**（范围 1–20，高级设置可调） | 最坏情况 200 个源同时到期：单请求 2 秒时约 80 秒跑完，单请求 10 秒时约 6.7 分钟 |
| 数据保留 | **90 天**（自动清理） | 典型规模落 30–65 万行 / 0.3–0.6 GB |
| 事件归档 | **14 天**无新增即归档 | 归档后不再参与比较 |
| 新鲜窗口 | **7 天**（可按源关掉或调整） | 只对「明确写了旧时间」的内容生效 |
| 全局判断模式 | **纯算法**（LLM 需用户主动开启） | 保证默认不产生任何 token 花费 |
| 打分两条线（占位） | 高 65 / 低 35（灰区 30 分宽） | 跑起来后按真实观察再调 |

规模测算（按每条约 1 KB 估算）：
- 50 个源 × 每小时 × 每轮 30 条、新内容占一成：新增 3600 条/天，90 天约 32 万行 / 0.31 GB；抓取 1200 次/天。
- 100 个源（常见上限）：新增 7200 条/天，90 天约 65 万行 / 0.62 GB；指纹查询约 7.2 万次/天（每秒不到 1 次）。
- 200 个源 × 每小时 × 每轮 60 条（极端）：90 天约 260 万行 / 2.5 GB。
- 200 个源 × 每 15 分钟 × 每轮 30 条（最极端）：90 天约 520 万行 / 5 GB —— 这种规模把保留天数或抓取频率调小即可，SQLite 本身扛得住。
- LLM 花费敏感度：新内容里进灰区的比例决定调用量，100 个源、灰区一成时约 720 次/天（约 0.4M token/天），灰区三成时约 2160 次/天（约 1.1M token/天）。所以默认不开 LLM，且灰区宜窄。

### 调度与并发的取舍（沿用上一代 Radar 的结论 + 这次的变化）

- **沿用不变**：不引入任何额外组件——不用 Redis、不用消息队列、不用向量数据库、不用 Elasticsearch（上一代 Radar 就定了这条，现在依然成立）。
- **要变的是并发**：上一代是一轮**串行**跑完就退出（有整轮时间预算，源一多，排在后面的要等很久）。Kestrel 是常驻服务、每个源有各自的抓取频率，会有多个源在同一时刻到期，所以必须**有限并发**（默认同时 5 个，可配），否则会互相排队。实现上不需要线程池那类框架，一个限制同时请求数的小工具就够。
- **「队列」用最朴素的方式实现**：一张待办表（谁该抓了、下次什么时候）加每个任务的执行状态（进行中 / 成功 / 失败 / 下次时间），都存在数据库里；进程重启后按库里的时间继续，**不补跑历史**（内容靠增量判定，漏一轮只会晚一点知道，不会丢内容）。
- 继续保留上一代已经验证过的东西：单源失败隔离（一个源挂了不影响别的源）、超时、有限重试、整轮时间预算、幂等去重（重跑不产生重复条目）。

## 11. 协作与开发纪律

- 每阶段测试先行、最小改动、可回滚；未经允许不得擅自改动或增加功能，须先确认。
- 分阶段推进，每个阶段完成后停下给实测结果，确认后再进入下一阶段。
- 开发开始时把本文件镜像进仓库（docs/），并拆分阶段计划。
- **判定逻辑要给开发者写清楚**：实现时补一份判定流程说明（漏斗四层、每层输入输出、分档规则、理由记录字段），让其他人看得懂设计思路，不用猜。
