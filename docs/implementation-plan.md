# Radar V2 分阶段实现计划

状态：草案，只有 Phase 0 已获授权；其余阶段需逐一确认

## Phase 0：规格冻结与旧项目只读映射

评审产品范围、场景和领域不变量；只读审查旧 Radar 模块与当前运行状态，形成复用矩阵、首版范围和待确认决定。不编写实现代码、不修改生产系统。

验收：每个场景有可执行验收条件；概念和调度无自相矛盾；所有未决选择明确列出。用户签字后冻结规格。

## Phase 1：独立运行骨架与只读 Web

先写失败测试，再实现 Docker 服务、配置加载、数据库迁移、只读 API 与三栏只读界面。数据使用隔离的测试库；不接外部来源、不发送消息。

## Phase 2：来源连接器与来源组

先实现统一连接器契约和通用 RSS/HTTP 来源，再按优先级加入 RSSHub/GitHub/Telegram。连接测试、映射预览、错误隔离、来源健康展示。每种来源独立验收。

## Phase 3：Watcher 与事件引擎

Watcher 多目标、多来源、版本化；纯规则模式、Item/Event 存储、幂等及查询。用旧 Radar 测试经验验证归并，但不直接改旧库。

## Phase 4：Action 与独立调度

采集、判断、即时动作、定时汇总独立调度；通知连接器、失败重试、幂等、审计。先在测试通道实发验证，不自动启用生产通知。

## Phase 5：LLM 辅助

Provider profile（远端 OpenAI-compatible / Ollama）、规则初筛、判断落库、可选合并辅助、失败与显式降级；使用真实模型测试前需单独预算与授权。

## Phase 6：Agent 接入与容量治理

REST 查询契约、可选只读 MCP 适配、TTL/数据库上限、清理保护及告警。回调与 Source webhook 均可后置。

## 阶段交接约束

每阶段：测试先行（先失败）→ 最小实现 → 自动化回归 → 实际运行/接口验证 → Git 提交 → 冻结验收 → 停下。cc 仅在用户确认具体阶段、预计调用次数与成本后使用；不让 cc 一次性重构全项目。

## 待用户确认的设计决定

1. 首版内置来源的具体实施顺序；Telegram 频道读取协议与授权方式需实际可行性验证。
2. Web/API 自定义解析器首版支持的字段映射、分页与认证方式。
3. 数据库引擎、默认 TTL、容量默认值与部署资源预算；用户可配置范围和硬边界。
4. 默认通知渠道以及定时汇总格式；是否与既有日报完全独立。
5. RSSHub 路由目录同步频率与“路由不存在”的判据，防止把暂时 404 当成永久删除。
6. Watcher 规则历史重评估时是否允许重发 Action（建议默认禁止）。
7. Agent 主动回调与 MCP 是否进入第一发布版，还是只提供 REST 查询。
8. Web UI 的登录方式、访问范围与外部暴露策略。

未确认的决定不得由实现 Agent 擅自选定为生产默认。
