# Radar V2 场景规格

状态：草案，待 Phase 0 评审冻结

## 场景 1：AI 资讯定时汇总

用户配置 GitHub、官方网站 RSS、RSSHub 路由和普通 RSS，组成“AI 官方来源”组。
Watcher 关注 AI 相关发布、公告和重大消息，先规则初筛，再可选用 LLM 判断相关性和重要性。事件进入池后，每天固定时间汇总发送到企业微信。

验收：采集频率与汇总频率独立；事件保存；单一 Action 失败不影响其他 Action；LLM 结果可追溯。

## 场景 2：目标对象的即时消息

用户配置某演员及其别名，关联电影数据库、新闻 RSS、网页/API 来源。Watcher 关注新作品或确认参演消息，命中后立即发送通知。

验收：一个 Watcher 可有多个来源和多个目标；事件显示命中的目标与证据来源；规则变更不删除历史。

## 场景 3：Telegram 内容监听

用户把 Telegram 频道作为采集 Source，配置目标和筛选规则。Radar 读取频道内容，产生标准化 Item；匹配后形成 Event，并执行已配置动作。

“Telegram Source（读取）”与“Telegram Action（发送）”是两个独立配置，不复用 Hermes 的 Telegram 聊天入口权限。

## 场景 4：用户主动查询

用户或 Agent 请求“最近目标相关消息”。调用方根据上下文确定时间范围、范围层级和数量，向 Radar 传递明确参数；Radar 只查询并返回结构化结果，不自动产生通知。

验收：支持 start/end、scope、limit 等显式参数；“最近”不在核心中硬编码为固定天数。

## 场景 5：RSSHub 路由失效

已配置的 RSSHub 路由返回 404、路由不存在或连续失败。

验收：来源变为 unavailable/degraded；页面显示最后成功时间、失败次数、受影响 Watcher；保留配置、历史 Item/Event；不静默删除、不自动篡改规则；恢复后可重新变为 active。

## 场景 6：规则修改

用户修改 Watcher 的来源、条件、处理模式或动作。

验收：生成新规则版本；新数据按新版本处理；历史判断和动作记录保留；默认不重跑历史；用户可显式选择时间范围重新评估。

## 场景 7：LLM 不可用

Watcher 配置为规则+LLM，模型服务超时或不可达。

验收：默认本轮失败并记录原因；按重试策略重试；仍失败时执行失败通知；若用户打开降级开关，才允许转为纯规则，并在结果中标注发生了降级。

## 场景 8：事件多动作

一个事件配置保存、即时通知、定时汇总三个动作。

验收：每个动作独立记录状态和重试；一个动作失败不影响其他动作；重复事件和重复动作有幂等保护。

## 场景 9：容量超限

数据库或某类数据达到用户设定上限。

验收：先清理过期日志、原始响应和已归档数据；保护活动 Watcher 相关数据及未完成 Action；仍超限时暂停低优先级采集并发出容量告警；不静默无限增长。
