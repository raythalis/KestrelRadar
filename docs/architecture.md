# Radar V2 技术架构约束

状态：草案，待 Phase 0 评审冻结。本文不是代码实现设计。

## 1. 部署

独立 Docker 应用：Web UI、服务 API、采集/判断/动作工作器和持久数据库可先在同一个服务进程中分模块运行；是否拆容器由实测负载决定。不得依赖 Hermes 进程或凭据。

生产数据与 Git 仓库分离，Docker Compose 使用宿主绑定目录（非匿名/命名卷），密钥独立管理，配置可备份与恢复。

## 2. 来源扩展

核心处理层只接收统一 Item 与连接器能力声明，不认识 RSSHub route 或平台字段。RSS/Atom、RSSHub、GitHub、Telegram、网页、HTTP API 为首版来源类别。

新增普通网页/API 优先通过认证、字段映射、分页和解析配置接入；非标准协议通过安装连接器插件扩展，不修改核心事件代码。“兼容所有源”定义为可扩展架构，不承诺任意未知来源零开发接入。

插件须有能力声明、版本、测试连接与隔离错误；不得直接读取其他来源凭据。

## 3. RSSHub

Radar 记录 RSSHub 实例、路由标识、参数与实际 feed URL，支持路由目录/元数据同步和真实抓取验证。目录存在不等于内容正确；HTTP 成功也不等于语义正确。目录路由消失或实际抓取失败时分别标注，避免误判短暂网络故障。

## 4. 数据层

至少区分：来源配置、来源组、Watcher 版本、Item、Event、判断记录、Action 执行记录、调度运行记录。原始证据与来源身份不可因事件合并消失。

数据库引擎、迁移机制、具体 schema 在阶段方案中确定，不把旧库直接当作新库。旧 Radar 数据先只读分析，再决定是否迁移。

## 5. 旧项目复用

`/opt/data/radar` 是参考实现：优先审查 feed 解析、URL 归一化、幂等采集、保守归并、故障隔离和测试夹具。逐项标注“可直接复用 / 需适配 / 不迁移”，用测试证明行为，不整包复制旧阶段概念。

## 6. 安全

Radar 自管来源、LLM、动作凭据。密钥不回显、不写日志、不进 Git；存储加密所需主密钥独立于数据库，部署时由受限环境/文件提供。浏览器不直接持有主密钥或外部 API 密钥。

网页/API 来源的任意 URL 需防 SSRF（阻止访问未授权内网/metadata 地址）、超时、响应大小和并发限制。Action 只能调用预先配置且授权的接口目标；通过接口也可能产生副作用，应有权限与幂等控制。

## 7. 运行纪律

按阶段测试先行；每阶段独立提交，报告真实测试和影响范围，冻结验收后停下。未经明确批准不修改旧 Radar、生产库、Cron、Hermes 或网络暴露。
