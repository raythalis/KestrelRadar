# Kestrel Radar · UX Writing / Content Design 规则

状态：**生效**。所有页面按这份规则写文案。

> 页面结构与信息层级另见 `docs/design/product-pages.md`（Design Lab ≠ 正式产品）。

## 零、与需求和实现对齐

界面**不承担「向用户解释这个功能是干什么的」的职责**。

- 功能范围与验收以已确认的需求为准；面向用户的文字必须反映当前实际可用的操作，不把尚未实现的计划写成现行能力。
- **功能验证阶段的页面同样按成品标准写文案**：不写「这是什么」「用来干嘛」，只写标签、状态、报错、影响范围。
- 如果一条文案的存在理由是「怕用户不知道这里是做什么的」，那它就是该删的那条。

## 一、核心原则

**界面应该自解释，而不是解释界面。**

判断标准只有一条：**删掉这句话，用户会不会做错？**
会 → 放到对的位置（字段 hint / tooltip / 空状态 / 危险操作确认 / 报错）；不会 → 删掉。

目标不是「少写字」，而是让用户通过界面本身理解产品，而不是让产品不断解释自己。

## 二、允许出现的文字（只有这四类）

| 类别 | 例子 | 位置 |
| --- | --- | --- |
| 标签 / 字段名 | 「通知渠道」「Bot Token」 | 字段自身 |
| 状态（短名词短语） | 「未选择通知渠道」「连通」「已停用」 | 状态位、卡片状态行 |
| 报错（一句话，说清哪里不对） | 「表达式要五段（分 时 日 月 周）」 | 字段下方 |
| 危险操作的影响范围 | 「还在用它的动作会发不出去」 | 删除确认里 |

## 三、禁止出现的文字

1. 教用户点哪里：「改完点这张卡的『保存』」「再点一次」。
2. 实现细节：「程序自己拼」「只会读，不会改库里的数据」「放在请求头 Authorization: Bearer」。
3. 为凑版面写的 description：卡片说明、页面副标题里对功能的泛泛介绍。
4. 同一信息的第二次表达：字段名已说明的，不再写一段解释；状态已有视觉的，不再写句子。
5. 版本/进度说明：「v1.0 只登记…」「仪表盘先占位…」。

## 四、写法约束

- 长度：状态 ≤ 8 字；字段 hint 一行（约 24 字）；报错 ≤ 一句；删除确认 ≤ 两行。
- 语气：中性、专业、现在时；不用「您」，不用感叹号，不卖萌，不写教程口吻。
- 术语：只在用户必须自己输入/判断时出现，并且出现即解释一句（例如「群是负数、私聊是正数」）。
- 示例值：只在没有它用户真的写不出来时给（例如「杨幂的新电影」这种自然语言输入示例）。
- 表述对象：写「用户要做什么」，不写「系统内部怎么工作」。

## 五、豁免

- `/style-lab`（开发环境的组件预览页）是开发/验收用的，不受本规则约束——它的说明文字是给实现者看的。
- 报错、空状态、删除确认里的事实性说明保留，但按上面的长度与语气收紧。

## 六、应用与自查

文案随页面一起改，不单独回头补。每个页面完成时自查四个问题：

1. 有没有在教用户怎么点击？
2. 有没有泄露实现细节？
3. 有没有把同一件事解释两遍？
4. 能不能换成状态标签？

规则对所有阶段（含功能验证阶段）一视同仁：一律按成品标准写文案，不为「让人看懂这是干嘛的」增加任何说明文字。
