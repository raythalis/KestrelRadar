# 使用手册

Kestrel Radar 的日常流程是：在分组中配置**发现**（从哪里采集）、**监听**（什么内容留下）、**动作**（什么时候发、发到哪里）；仪表盘用来查看形成的事件和异常。这篇按实际界面任务组织，安装与第一次跑通先看[快速开始](getting-started.md)。

## 第一次使用：建立一个分组

进入**配置管理**，点“新建分组”，填写名称，可填写简介，然后保存。分组展开后有发现、监听、动作三列；同一分组可以添加多条。分组可收起、展开、编辑和删除。停用分组会停止这组的采集与后续处理，已有数据不因停用而删除。删除前请读确认弹窗；不要把“停用”和“删除”混用。

## 添加发现与设置采集计划

在目标分组的**发现**列点新增，填名称、类型、目标地址/路由和采集频率：

- **RSS 源**：完整 RSS/Atom 订阅地址，以 `http://` 或 `https://` 开头。
- **RSSHub 路由**：路由路径可以写成 `/命名空间/路由`；实例基础地址在**设置 → 采集**配置，不是每个发现分别填。
- **网页地址**：完整网页地址；程序会尝试从页面的 RSS/Atom 声明中找到订阅源。普通网页没有可发现的订阅源时，不等于能抓取任意网页正文。

### RSSHub 是什么，怎么找路由

[RSSHub](https://docs.rsshub.app/zh/) 是将网站内容转换为 RSS 订阅源的独立项目。Kestrel Radar 不内置 RSSHub，也不替它抓取任意网站：选 RSSHub 路由时，Kestrel Radar 按采集计划向你配置的 RSSHub 实例请求订阅内容，再交给监听判定。网站本身已有 RSS/Atom 地址时，可以直接选“RSS 源”，无需 RSSHub。

到 [RSSHub 官方路由列表](https://docs.rsshub.app/zh/routes/) 搜索目标网站，打开具体路由说明，按说明填写必需参数并取得实际路径；路径格式与实例地址的关系见[官方入门说明](https://docs.rsshub.app/zh/guide/#生成订阅源)。在 Kestrel Radar 中把实例地址填到**设置 → 采集 → RSSHub 地址**，把路由路径填到发现的“RSSHub 路由”目标；两者由 Kestrel Radar 组合。若实例要求访问密钥，也在同一处设置。实例和目标路由都需要从**运行 Kestrel Radar 的环境**可访问，部分路由还要求凭据、浏览器渲染或受目标站反爬影响；路由在文档里存在不代表你的实例当前一定能采到。先测设置里的实例连接，再保存发现并用“测试采集”验证目标内容。

采集频率字段可点开生成器选时间，也可填五段 cron 表达式。它决定**多久检查一次**，不是每次只读取多少小时的内容。保存后到卡片上点“测试采集”：它检查路由与内容，结果通过浮层反馈；**测试不写入条目**。当前创建流程**不会在保存前自动测试**，也没有独立的“对尚未保存的目标测试”入口。

启用的发现会按自己的计划采集。第一次成功采集建立基线，把当时见到的内容作为历史；后续新出现的内容才进入判定与投递流程。重复采集到同一条不会再次算作新内容。编辑发现可改目标或频率、启停；删除发现前界面提示其历史条目和事件保留。

## 创建监听与判断内容

在同一分组的**监听**列新增监听，设置名称、模式、关键词、匹配方式、灵敏度及排除词：

- 关键词选“任意命中”或“全部命中”；留空表示不加关键词门槛。排除词可追加全局排除词。
- 模式可“跟随全局”、只用算法，或用 **LLM+**。LLM+ 的意图描述只在适用的模式下出现；启用模型判定前需先配置供应商、调用顺序和全局判定设置，见[配置](configuration.md)；判定细则见[打分规则](judgment-scoring.md)和[LLM+](llm-plus.md)。
- “指定关联动作”留空时跟随同分组动作；选中动作则仅由所选动作处理这条监听的命中。

监听判定发生在**新条目采集后**，不是改了规则就自动重判所有历史条目。当前配置页可新建/编辑/删除监听，但**没有可用的监听规则预览或试跑入口**；旧阶段文档中描述的预览接口不要当作界面功能。只想先观察，可在不配置投递动作时查看后续事件，但仍需要等待真实的新内容。未通过的条目不形成事件；目前仪表盘不是所有原始条目的查询页。

## 配置动作与消息模板

在分组的**动作**列新增动作，设置名称、触发方式、通知渠道和模板。触发方式有“采集到就投递”和“每天汇总”；后者额外需要汇总时间。可选“合并为一条消息”；每天汇总还可选是否包含已经即时投递过的内容。渠道未选择或已停用时不会发出通知。

**设置 → 投递**中管理消息模板：内置默认模板只读，自定义模板可新增、编辑和删除。动作里选择模板；不选或所选模板已删除时，后端使用同一份内置默认正文，不是按界面语言维护的两套正文。模板支持 `{{title}}`、`{{summary}}`、`{{url}}`、`{{sourceCount}}`、`{{sources}}`、`{{hitAt}}`、`{{group}}`、`{{badge}}`、`{{eventCount}}`；变量由投递时填入。模板正文与投递语言设置不同：切换界面语言不会自动翻译你写的模板。Webhook 投递是 JSON POST，配置了密钥时使用 Bearer 凭据；请求包含渲染后的正文、事件标题、原文链接、来源数量、消息中事件数量和命中时间。接收端返回 2xx 才算成功。

一条内容对同一动作不会因重复采集而反复投递。已投递的同一事件有新来源时默认也不再投递；只有符合代码识别的显著新进展，才可能标记为“有更新”并再次投递。汇总取尚未由该动作投递的命中，不是对指定时间范围重新扫描一遍。

## 配置与测试通知渠道

**通知渠道**页支持 **Telegram** 与 **Webhook**；可以创建多个实例，分别编辑、停用或删除。Telegram 配 Bot token 和会话 ID；先让 bot 在私聊收到消息或加入并接收群消息，再使用“读取会话”选择，也可手填会话 ID。Webhook 配接收地址，可选密钥；协议细节见[配置](configuration.md)。

渠道卡的“测试”会**真的发出测试消息**，请确认目标会话或接收端再点。成功或失败通过浮层反馈，卡上有本次测试状态；修改渠道凭据后旧测试状态作废。渠道测试不等于采集与监听已经成功。删除一个仍被动作引用的渠道会让这些动作无法投递。

## 配置模型与全局设置

**模型**页添加 Ollama 或 OpenAI 兼容供应商，填写接口地址，按需填写 API Key；模型调用顺序从供应商实际返回的模型清单选择，最多三行，保存后生效。取不到模型清单的供应商不会出现在可选模型中。全局判定默认纯算法，不配置模型也能运行；要用 LLM+，还需在**设置 → 判定**选择模式，并按需调整超时、重试和失败降级。模型请求可能产生供应商费用。

**设置**页分通用、判定、采集与保留、投递、关于几个标签。各设置卡先修改草稿，再点本卡的“保存”；本卡的“重置”只撤销**未保存**的改动、回到已保存值，**不是恢复出厂默认**。RSSHub 地址旁的测试读取当前输入但不保存设置。界面语言由本浏览器的偏好保存；其他全局设置由后端保存。具体配置项见[配置](configuration.md)。

## 查看事件和异常

**仪表盘**已有真实统计，以及最近 24 小时内的事件列表和异常记录，并非占位页面。事件可按发现筛选；点事件可打开有链接的原文并标为已读。列表头“查看全部”展开列表，继续滚动加载更多；这里的“全部”仍受最近 24 小时窗口限制，**不是所有历史原始条目**。一条事件可包含多个来源，来源标签或 `+N` 列表可查看各自链接。

异常区展示采集、判定或投递等失败信息；“忽视”把该异常从当前列表移走，**不等于修复根因**。若事件、统计、异常某块读取失败，其他块仍可单独显示；留意界面浮层的请求错误。

## 为什么没有事件或通知

按链路逐项检查，而不是只测渠道：

1. **没有采到新内容？** 看分组与发现是否启用、采集频率、目标是否可读，并在发现卡点“测试采集”。测试只探测、不入库；首次正式采集只是基线。RSSHub 路由还要核对实例地址对运行环境是否可达。
2. **有新条目但无事件？** 核对同组监听是否启用、关键词任意/全部、排除词与灵敏度；LLM+ 时检查模型供应商、调用顺序和失败降级。事件归并只接收判定通过的条目，未判或被丢弃的内容不会出现在最近事件里；事件列表还只看最近 24 小时。
3. **有事件但没收到消息？** 核对同组动作启用、触发方式（即时或待汇总时间）、监听是否只关联了别的动作、渠道是否启用。检查新鲜窗口、每日投递上限及“已经由这个动作投递过/同一事件默认不重复投递”的规则。渠道测试消息成功不代表有满足条件的业务命中。
4. **曾经投递失败？** 看仪表盘异常与渠道测试反馈，修正地址、会话或凭据后等待下一次合适的触发；不要把“忽视异常”当成重试或修复按钮。

目前界面**没有完整原始条目浏览器或逐条判定理由检索**，也没有“立即采集并立刻投递”的用户按钮；不要用旧需求中的计划功能判断现行产品。
